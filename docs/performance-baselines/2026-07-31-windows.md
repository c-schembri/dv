# Windows Reference Baseline - 2026-07-31

This is observed evidence from one uncontrolled developer machine. It is not a
cross-machine target.

## Machine

- Windows 11 `10.0.22631`, x86-64
- AMD Ryzen 9 9900X, 12 cores, 24 hardware threads
- .NET SDK `10.0.100`
- initial foundation `dv` binary size: 182,784 bytes
- post-project-evaluator `dv` binary size: 453,632 bytes
- evaluator measurement state: working tree based on commit `583200710f93`
- power plan, background load, CPU frequency, and OS page-cache state were not
  controlled

## Startup

Thirty retained samples after three warm-ups:

| Tool | Case | Min | Median | p95 | Max |
|---|---|---:|---:|---:|---:|
| `dotnet` | `--version` | 60.203 ms | 62.451 ms | 66.332 ms | 66.473 ms |
| `dv` | `--version` | 2.715 ms | 3.034 ms | 3.364 ms | 3.651 ms |

This proves only the current Phase 0 version path and process-launch cost. It
does not predict build performance.

The direct help/version classifier removed avoidable owned argument collection
from this path. A preceding 30-sample run measured a `2.988 ms` median; the
final run measured `3.034 ms`. That difference is noise at this sample size, so
no performance improvement is claimed. The structural allocation removal is
retained because the work is unnecessary and the path is simpler to cost.

## SDK Selection

Thirty retained samples after three warm-ups. The harness first verified that
both commands selected `10.0.100`:

| Tool | Command | Min | Median | p95 | Max |
|---|---|---:|---:|---:|---:|
| `dotnet` | `dotnet --version` | 61.036 ms | 63.050 ms | 66.537 ms | 66.760 ms |
| `dv` | `dv sdk current` | 3.086 ms | 3.451 ms | 4.300 ms | 4.865 ms |

The `dv` path performed native root discovery, enumerated three installed SDK
directories, parsed their versions, and selected the highest compatible SDK.

After adding the native project evaluator and its XML parser, the like-for-like
SDK case was measured again:

| Tool | Command | Min | Median | p95 | Max |
|---|---|---:|---:|---:|---:|
| `dotnet` | `dotnet --version` | 64.260 ms | 65.841 ms | 69.283 ms | 69.896 ms |
| `dv` | `dv sdk current` | 3.148 ms | 3.698 ms | 4.450 ms | 4.493 ms |

The difference from the earlier run includes binary-layout changes and
uncontrolled machine noise. It is not isolated as a parser cost.

After adding .NET 10 compiler input planning, the current release binary was
measured again:

| Tool | Command | Min | Median | p95 | Max |
|---|---|---:|---:|---:|---:|
| `dotnet` | `dotnet --version` | 60.436 ms | 62.959 ms | 68.050 ms | 68.509 ms |
| `dv` | `dv sdk current` | 3.087 ms | 3.389 ms | 4.033 ms | 4.096 ms |

After adding package resolution, ZIP validation, and TLS-backed NuGet v2/v3
clients, the final release binary was 2,570,752 bytes and was measured again:

| Tool | Command | Min | Median | p95 | Max |
|---|---|---:|---:|---:|---:|
| `dotnet` | `dotnet --version` | 59.532 ms | 60.637 ms | 61.595 ms | 61.654 ms |
| `dv` | `dv sdk current` | 3.533 ms | 3.798 ms | 4.322 ms | 4.349 ms |

The 2.1 MB increase from the post-evaluator binary is primarily the cost of
pure-Rust TLS, HTTP, SHA-512, and ZIP support. The SDK command does not
initialize or use those subsystems, but linked code and binary layout still
affect one-shot process measurements. Its median remains below the local 5 ms
budget.

## Project Evaluation

The current `net10.0` fixture and release binary were measured with thirty
retained samples after three warm-ups:

| Tool | Min | Median | p95 | Max |
|---|---:|---:|---:|---:|
| `dotnet` | 284.063 ms | 296.365 ms | 333.900 ms | 340.625 ms |
| `dv` | 2.965 ms | 3.299 ms | 3.785 ms | 3.959 ms |

The final package-enabled binary was remeasured:

| Tool | Min | Median | p95 | Max |
|---|---:|---:|---:|---:|
| `dotnet` | 276.853 ms | 282.186 ms | 287.600 ms | 287.930 ms |
| `dv` | 3.408 ms | 3.846 ms | 4.074 ms | 4.103 ms |

Exact commands:

```text
dotnet msbuild SmallConsole.csproj --nologo -getProperty:TargetFramework,OutputType,Nullable,ImplicitUsings,AssemblyName,RootNamespace,Configuration,Deterministic -getItem:Compile,ProjectReference,PackageReference
dv project inspect SmallConsole.csproj --json
```

Before timing, the harness compared target framework, output type, nullable,
implicit usings, assembly name, root namespace, configuration, deterministic
mode, and ordered compile items. Both tools evaluated the same meaningful
project data.

The `dv` median is below the observed Windows process-launch floor from the
adjacent self-version samples. That does not imply negative evaluator cost;
sub-millisecond process-launch variation is larger than this project transform.

## Compiler Input Planning

Thirty retained samples after five warm-ups:

| Tool | Min | Median | p95 | Max |
|---|---:|---:|---:|---:|
| `dotnet` | 370.501 ms | 379.938 ms | 408.786 ms | 422.491 ms |
| `dv` | 4.613 ms | 5.292 ms | 6.184 ms | 11.463 ms |

The final package-enabled binary was remeasured:

| Tool | Min | Median | p95 | Max |
|---|---:|---:|---:|---:|
| `dotnet` | 364.607 ms | 368.952 ms | 374.293 ms | 377.630 ms |
| `dv` | 4.672 ms | 4.979 ms | 6.027 ms | 6.334 ms |

Exact commands:

```text
dotnet msbuild SmallConsole.csproj --nologo -t:ResolveReferences -getProperty:LangVersion,DefineConstants -getItem:ReferencePath,Analyzer,Compile
dv build --plan SmallConsole.csproj --json
```

The untimed preflight restored a mutable fixture copy, then compared C#
language version, ordered defines, user sources, 167 framework reference paths,
and 8 analyzer paths. Both timed commands include structured JSON reporting.
The median ratio is `71.8x`; this is an end-to-end process measurement, not a
claim that XML parsing itself is 85.5 times faster.

## Reference Workflows

Ten retained samples after two warm-ups using `small-console`:

| Tool | Case | Min | Median | p95 | Max |
|---|---|---:|---:|---:|---:|
| `dotnet` | cold project restore | 477.993 ms | 484.502 ms | 495.556 ms | 495.556 ms |
| `dotnet` | clean build after untimed restore | 543.458 ms | 567.595 ms | 598.390 ms | 598.390 ms |
| `dotnet` | no-op build | 448.845 ms | 467.037 ms | 511.183 ms | 511.183 ms |
| `dotnet` | warm run with no build/restore | 316.930 ms | 320.530 ms | 328.849 ms | 328.849 ms |

`restore_cold` means a fresh project copy. It does not flush OS or NuGet caches.
Fixture copying and clean-build restore were outside their named timed
intervals.
